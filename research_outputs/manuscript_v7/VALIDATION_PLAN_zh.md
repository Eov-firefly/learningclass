# v7 验证逻辑与待补材料

状态：本文件是修订阶段提出的验证计划，不是已执行的结果，不属于原 v5.1 冻结协议。任何新增分析须标为回顾性/探索性；新实验在查看新结果前另存计划及版本哈希。

## A. 首先补充已有归档

优先提供：原始 runner、core.py、engine.py、解析器、分析脚本、配置及依赖版本；冻结协议与执行时间证据；各阶段 question ID/抽样清单；25,200 次逐调用记录及原始汇总；完整诊断提取和计时补充表。可提供 ZIP 或仓库路径，无须先整理成新的漂亮报告。

逐调用记录建议保留以下字段；这是建议接口，不假定原始文件已经采用这些名字：stage、task、question_id、model_revision、policy、repeat、prompt/config hash、generated_token_ids、decoded_text、gold_answer、stop_reason、actual_generated_tokens、returned_tokens、generation_ms、end_to_end_ms、run/session ID、execution_order。

同一 question_id 必须在任务/模型/阶段中明确作用域；保留失败、重试和最终采用记录，不可只交成功样本。不要提供凭证或私有人类审核密钥。

## B. 无需新增 GPU 的优先分析

### B1. 合同敏感性与交付质量

研究问题：114 个严格合同收益在其他合理消费规则下是否仍有意义？

在同一批主实验返回文本上，分别计算严格终止合同、作者既有宽松提取器，以及明确实现的结构验证。结构规则需在批量查看结果前确定；若允许闭合 wrapper，不得悄悄修改原主终点，应作为额外分析列出。

合同设计需同时说明接受条件、值提取、EOS/换行处理、允许的特殊 token、多 marker、代码围栏/LaTeX、无效输出处理及是否在线可判定。报告 valid、correct、配对 win/loss 和置信区间；不得只选对 Complete 有利的合同。

独立语义审核与规则解析分开报告。人类评估不是所有格式合同研究的通用前提，但若主张实际答案更可用，应提供对应语义或消费任务证据。

### B2. 全量配对错误分类

覆盖所有正确性不一致对，而非只展示收益。至少区分：后续格式闭合、后续解释、重复 marker、答案修正、cap 未完成、其他/无法判定。分类标签、原始片段、两个策略的预测、有效性和判定理由应能逐项回查。

公开有代表性的完整上下文，不只截取 marker 一行。若出现早期错误答案、后续纠正的损失，照实报告；它直接检验 Proposition 2。

### B3. 共同轨迹检查

按任务、模型、问题配对，逐 token 验证 Complete 是 Uniform 前缀、Shadow 与 Complete 完全相同、Conjunction 不早于 Complete；明确包含 EOS 的计数规则。相同最终答案不等于相同 token 路径。

如果发现路径分歧，单独报告，并停止对该子集套用共同轨迹下的归因。理论条件不能靠 greedy 标签代替验证。

### B4. 重算统计

从逐调用记录重建全部5张表、二元区间及连续指标 bootstrap；保留原冻结方法和随机种子。新增合同/消融属于新比较族，预先指定主要比较或标为探索性，不沿用旧四项比较的“已校正”标签。

对 2 个百分点非劣界值补充实际应用理由，或将结果表述为对预设容忍度的分析，不暗示已经证明应用上可接受。

## C. 可能需要局部补跑的机制检验

### C1. 门控轨迹

最小字段为 step、completion flag、minimum-step flag、entropy stability flag、最终 conjunction flag、触发/终止原因。熵差、平滑状态及索引可用时一并保留。

统计各门单独满足的比例、完成机会数、重叠机会数及阻断原因。需要区分 EOS 同一步触发与严格提前触发。

如果现有记录未保存 logits/熵轨迹，不能从最终文本推断精确熵；可重新推理或对已保存 token 作受控前向重算，并报告这属于新的诊断运行及其数值条件。重算诊断不能冒充原执行 trace。

### C2. 单因素消融

固定模型、输入和生成配置，逐项改变：阈值0.01/0.05、最小步数、稳定窗口、候选前缀是否混入 prompt、触发索引及应用时刻。优先检验能解释现有失效的因素，不强制穷举所有组合。

修改后的策略使用新标识，保留 Legacy 原始结果；不能用修复结果覆盖旧实验却继续声称全程冻结。

### C3. 实用控制

加入直接可用的边界停止对照，并说明它与 Complete 是否实质相同。若相同，应承认 Complete 是该工程策略的实现，不为增加基线数量另起名称。

可加入只检测边界但不停止的边界 Shadow，以量化边界回调成本；加入与 Complete 输出相同的熵观察，以量化额外监测路径。只有输出相同的比较才可排除生成内容变化。

若测试完成状态锁存，必须声明返回的是当前文本还是历史缓存前缀。报告实际生成/返回 token、额外缓存和耗时，禁止只按截断后返回长度声称节省计算。

## D. 独立计时验证

目标是检验当前0.38%–1.24%开销能否跨会话复现，而非只增加同会话调用数。

先做可承受的独立会话试跑，依据题内与会话间变异、预设有意义差异决定后续规模。不要凭空指定足以证明效果的样本量。保留所有会话、预热策略、设备状态、随机顺序和同步边界。

报告每会话对比和汇总不确定性；若以会话为泛化对象，需要在分析中保留该层级。CPU/GPU profiler 本身可能扰动时序，应分离剖析运行与正式计时。

## E. 人工评估与外推实验

沿用原有独立双人盲评设计时，保留抽样层、纳入概率、未裁决评分和一致性；分歧富集样本的总体估计需按实际设计加权，不能随意套简单平均。数据不足时只报告诊断样本结论。

多预算、模型族、并发、后端或硬件实验根据目标主张选择。当前窄范围稿优先解决合同有效性和机制识别，不以调用数量替代研究问题。

## F. 写作更新规则

| 新证据 | 允许更新的主张 | 仍不能推出 |
|---|---|---|
| 多合同重评后收益稳健 | 对已测合同的稳健性 | 任意接口通用有效 |
| 语义/消费任务验证支持收益 | 对该目标人群或应用的交付改善 | 推理能力本体提高 |
| 门控trace与单因素消融一致 | 所测门控失效机制 | 熵停止普遍无效 |
| 多独立会话重现开销 | 当前实现开销的会话稳健性 | 熵计算的硬件下界 |
| 多预算/模型验证 | 对所测范围的外推增强 | 最优动态调度 |

每次补充后同步更新摘要、贡献、方法、结果、讨论和数据可用性，避免正文一处限制、另一处泛化。保留新旧分析版本和失败记录。
